# He Design 输出合同

## 目标

这个文件定义 `he-design` 在不同任务下应如何稳定输出，避免每次都只给抽象意见，或直接跳到代码而缺少设计判断。

## 默认输出顺序

除非用户明确只要代码、只要点评或只要一段简答，否则优先按下面 6 段输出：

1. 设计判断
2. 页面骨架
3. 视觉规则
4. 交互规则
5. 开发约束
6. 自检结论

## 1. 设计判断

至少回答：

- 页面目标属于什么表达类型
- 推荐视觉范式是什么
- 推荐页面原型是什么
- 当前信息密度属于什么等级
- 是否需要素材，以及素材角色是什么

推荐格式：

```md
## 设计判断
- 页面目标：发布型 / 说明型 / 传播型 / 应用界面
- 视觉范式：`brand_release` / `info_editorial` / `campaign_visual`
- 页面原型：`hero_release` / `feature_grid` / `editorial_explain` / `dashboard_polish` / `form_workspace`
- 信息密度：`low` / `medium` / `high`
- 素材策略：`none` / `mood` / `recognition` / `proof`
```

## 2. 页面骨架

至少回答：

- 页面主命题
- 一级区块顺序
- 每个区块的角色
- 哪些内容应删减或降级

## 3. 视觉规则

至少回答：

- 主标题与次级文字的层级
- 区块间节奏与留白
- 卡片、列表、图片区的统一规则
- 色彩、材质、图标语言建议

## 4. 交互规则

至少回答：

- 主操作和次操作分别是什么
- 需要哪些状态反馈
- 是否需要动效，以及动效只解决什么问题
- 哪些交互必须弱化，避免干扰主结构

## 5. 开发约束

如果用户下一步可能落代码，这一段不要省略。至少包含：

- 建议组件拆分
- 样式 token 方向
- 响应式结构变化
- 数据驱动位置
- 哪些部分适合先静态实现，哪些必须预留状态

## 6. 自检结论

至少回答：

- 当前最容易失控的点
- 必须优先守住的设计原则
- 如果只能先改一件事，应该改什么

## 代码场景附加规则

当用户直接要求“给我代码”时，也不要省掉设计判断，至少要先用短版给出：

1. 页面目标
2. 页面原型
3. 视觉重点
4. 组件拆分

然后再进入实现。

## 简答场景压缩规则

如果用户只问一句很短的问题，例如“这个页面为什么不高级”，可以压缩输出，但仍尽量保留：

- 核心问题判断
- 骨架问题
- 一个最关键修正方向

## 禁止的输出倾向

- 只给一堆风格形容词，不解释结构
- 一上来直接写代码，没有设计判断
- 同时给太多互相冲突的方向
- 把素材、美术和交互都抬到与主命题同一优先级
